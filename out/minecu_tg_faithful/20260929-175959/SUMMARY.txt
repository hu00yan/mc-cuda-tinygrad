--- what these numbers are, and are not ---
  * The three columns are RENDERS. Same world, same cameras, same
    max_steps, same uint8 observation, same card, same run, equal batch.
    `f/clean` is the crossing cost and is the number this arm adds; the
    two `*/ref` columns are render-against-render and are the same
    comparison `notes/19` §5.2 makes.
  * The two ms columns are DEVICE time -- the sum of the per-kernel
    device times in the graph, measured with tinygrad's own time_call,
    host tracing excluded. The reference's us figure is a cudaEvent
    median around a single launch, which is also device time and is the
    like-for-like comparison. The host build+realize figure printed
    beside each row is CONTEXT: it includes the framework's graph
    tracing, which the reference does not pay, so it is NOT divided by
    anything here.
  * Calling realize() on an already-realized tensor is a silent no-op.
    An earlier version of battery.py timed exactly that and reported the
    port at 0.011 ms against the reference's 152 us -- a 13x speedup over
    hand-written CUDA, from a graph whose offline SASS is tens of times
    the reference's instruction count. time_graph now raises if handed a
    realized tensor, and the timing instrument is minecu_tg's own
    linear_device_time_ms, which is the code path `notes/19` measured
    with. That false number is the reason the clock is named on every
    row rather than in a footnote.
  * The reference's whole-step figure is printed for context and is NOT a
    denominator anywhere. `4.55 M env-steps/s` covers 7 launches.
  * `same obs` compares the two modes' observations by sha256. Both are
    verified against the same float64 transcription and the same naive
    port, so a False here would mean the crossings changed the
    computation, and the ratios above it would be between two different
    computations.
  * The ratio to the reference is NOT attributed to the compiler unless
    both sides did the same work. Each mode's mean steps/pixel is in the
    battery output. The reference's own DEVICE-side step count is NOT
    available here: it needs the dda_probe_kernel from
    minecu_ref/bench/bench.cu, which refdrv.cu does not link, and putting
    the CPU model's number under the same label would be a claim about a
    device that was not measured. The workload check is one-sided and
    the note says so rather than rounding it up.
  * The obs_sha256 in the battery is this port's. verify.py proved it
    equals the naive port's and a float64 transcription's ON THIS CARD in
    this run. It is NOT compared against the reference's dumped bytes
    here; that is notes/19's comparison on the reference's own state, and
    this arm did not re-derive it.
  * No SASS number is reported here. The instruction and register counts
    come from the offline archlab route on the host, where ptxas and
    cuobjdump exist and nvcc's version is pinned; the T4 image's CUDA
    version is recorded but not used for a count.
