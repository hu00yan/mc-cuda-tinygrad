3. the table: 64 slab(s) of [64,64], on the card
==============================================================================
  MEASURED on this device.
  launches  GlobalCounters.kernel_count -- kernels the device actually ran.
  kernel_us sum of the per-kernel CUDA-event times tinygrad PRINTS at DEBUG=2.
            DEBUG=2 sets ExecContext.wait (realize.py:318), and ops_cuda.py:26-35
            then records an event, launches, records a second event and
            SYNCHRONISES on it -- so the graph is serialised and each number
            contains that kernel's host launch latency. That is the instrument,
            not the card, and it is why the per-launch calibration in section 5
            is needed to subtract it.
  copy_us   time_sum_s minus kernel_us. exec_copy returns no elapsed time, so
            realize.py:78-81 charges every COPY its HOST cost into time_sum_s.
            It is a real cost and it is not device time.
  t_sched   HOST wall clock of Tensor.schedule_linear() on its own fresh graph.
  t_exec    HOST wall clock of Tensor.realize() + synchronize() on its own
            fresh graph. Never on a graph already through schedule_linear():
            that MUTATES it (tensor.py:409-411) and the realize is then a
            silent no-op. How many kernels each timed realize launched is in
            ut_time.json, and a zero aborts the run.

4. shape sweep: launches should not move with slabs; arithmetic should
==============================================================================
  If the schedule is a function of the graph and not of the batch size, then
  `launches` is flat in slabs and only the per-slab arithmetic grows. Fitting
  kernel_us(slabs) = fixed + slope*slabs therefore separates the two axes
  WITHOUT converting an instruction count into time by any constant.

  `fixed` is the launch-dominated floor and `slope` the marginal per-slab
  cost. `ns/MAC` is nanoseconds of device time per algorithmic multiply-add.
  If that number is roughly the same for two candidates, device time tracks
  the ALGORITHM's arithmetic. If it differs by an order of magnitude between
  them, device time is tracking the SCHEDULE and the arithmetic column is not
  what the card is spending its time on. `launches flat` is the precondition
  for reading the fit this way at all, and it is reported per candidate.

5. launch calibration: what does one launch cost on this card?
==============================================================================
  A chain of n dependent one-op kernels, timed with the SAME instrument as
  the candidates (DEBUG=2, per-kernel CUDA events). The slope of kernel_us
  against the number of kernels that ACTUALLY LAUNCHED is microseconds per
  launch. This is the number that lets
      non_launch_us = kernel_us - launches * per_launch_us
  be a residual in MICROSECONDS rather than an instruction count times a
  constant -- which is what the census's non-additivity demands.

     shape      n  launched   kernel_us  us/launch
--------------------------------------------------
  1 thread     16        16         194     12.152
  1 thread     64        64         750     11.717
  1 thread    256       256       2,911     11.371
  1 thread   1024     1,024      11,735     11.460
  1 thread   4096     4,096      45,247     11.047
  1 thread    fit                           11.033   intercept 128 us, R2 0.9999

     16 KB     16        16         195     12.176
     16 KB     64        64         731     11.425
     16 KB    256       256       2,975     11.620
     16 KB   1024     1,024      11,700     11.426
     16 KB   4096     4,096      46,954     11.463
     16 KB    fit                           11.460   intercept 6 us, R2 1.0000

  MEASURED, DEBUG=2, so these slopes INCLUDE the host launch latency the
  instrument charges to every kernel -- which is exactly what the candidate
  measurements are charged too, so the residual below compares like with like.
  The chain has ONE copy per realize, not one per step, so the intercept
  absorbs the copy's host cost (realize.py:78-81) and the slope does not.
  The `16 KB` row is a sensitivity check: it is what a candidate kernel of
  this operator's size costs if it did NOTHING but move one buffer. The
  headline uses the `1 thread` row.

== residual: kernel_us - launches * per_launch_us   (bench shape) ==
cand  launches  kernel_us  launch_us     @16KB   resid_us   resid %   ns/algMAC  reading
----------------------------------------------------------------------------------------
A        5,380     91,175     59,358    61,655     31,816     34.9%       1.271  launch-dominated
B           86      2,765        949       986      1,816     65.7%       0.073  not-launch-dominated
C           44        840        485       504        355     42.2%       0.084  launch-dominated
D2          41      1,483        452       470      1,031     69.5%       0.010  not-launch-dominated

  `launches` here is the DEVICE launch count, which includes the COPYs. A COPY
  costs no device time at all (exec_copy returns no elapsed time), so the
  launch term slightly over-charges every candidate. The number of COPYs is in
  ut_time.json per candidate; subtracting them changes the launch term by a few
  percent and moves no row across the 50% line.

  ns/algMAC is nanoseconds of NON-LAUNCH device time per algorithmic
  multiply-add, using the algorithm's own MAC count (ut_price.macs) and not
  any census figure. Candidates whose entries agree are being priced by the
  same axis; candidates whose entries differ by an order of magnitude are
  not, and THAT is the finding, not the winner.
