4. shape sweep: launches should not move with slabs; arithmetic should
==============================================================================
  If the schedule is a function of the graph and not of the batch size, then
  `launches` is flat in slabs and only the per-slab arithmetic grows. Fitting
  gpu_us(slabs) = fixed + slope*slabs therefore separates the two axes WITHOUT
  converting an instruction count into time by any constant.

  `fixed` is the launch-dominated floor and `slope` the marginal per-slab
  cost. `ns/MAC` is nanoseconds of device time per algorithmic multiply-add.
  If that number is roughly the same for two candidates, device time tracks
  the ALGORITHM's arithmetic. If it differs by an order of magnitude between
  them, device time is tracking the SCHEDULE and the arithmetic column is not
  what the card is spending its time on.

  `launch_counts` per candidate, across the sweep, are in ut_time.json.
  If they are not flat in slabs, the fit above does not separate the two
  axes the way this section claims, and the note must say so.

5. launch calibration: what does one launch cost on this card?
==============================================================================
  A chain of n dependent one-op kernels, timed with the SAME instrument as
  the candidates (DEBUG=2, per-kernel CUDA events). The slope of gpu_us
  against the number of kernels that ACTUALLY LAUNCHED is microseconds per
  launch. This is the number that lets
      arithmetic_us = gpu_us - launches * per_launch_us
  be a residual in MICROSECONDS rather than an instruction count times a
  constant -- which is what the brief asks for, since the census is not
  additive and converting it by a factor would be the error.

     shape      n  launched      gpu_us  us/launch
--------------------------------------------------
  1 thread     16        16         311     19.426
  1 thread     64        64         826     12.902
  1 thread    256       256       2,903     11.341
  1 thread   1024     1,024      11,164     10.902
  1 thread   4096     4,096      43,948     10.729
  1 thread    fit                           10.693   intercept 162 us, R2 1.0000

     16 KB     16        16         314     19.650
     16 KB     64        64         836     13.060
     16 KB    256       256       2,993     11.690
     16 KB   1024     1,024      11,796     11.519
     16 KB   4096     4,096      45,157     11.025
     16 KB    fit                           10.986   intercept 231 us, R2 0.9999

  MEASURED, DEBUG=2, so these slopes INCLUDE the host launch latency the
  instrument charges to every kernel -- which is exactly what the candidate
  measurements are charged too, so the residual below compares like with like.
  The `16 KB` row is a sensitivity check: it is what a candidate kernel of
  this operator's size costs if it did NOTHING but copy one buffer. The
  headline uses the `1 thread` row.

  ns/algMAC is nanoseconds of NON-LAUNCH device time per algorithmic

  any census figure. Candidates whose entries agree are being priced by the
  same axis; candidates whose entries differ by an order of magnitude are
  not, and THAT is the finding, not the winner.

7. is the ordering spelling-invariant?
==============================================================================
  notes/31 §2: the `numpy` spelling of a constant costs a COPY kernel each and
  the `arange` spelling costs ALU inside every consumer. notes/31 measured the
  KERNEL ranking to be identical under both. The TIMING ranking is checked here,
  for the two candidates the open question is actually about.

spelling  cand  launches      gpu_us  t_realize_ms
--------------------------------------------------
arange    C           44       2,369           0.1
arange    D2          41       2,385           0.1

numpy     C           71       3,488           0.1
numpy     D2          64       3,378           0.1

  spelling arange  gpu_us: C 2,369 vs D2 2,385  ->  C is faster  (1.01x)
  spelling numpy   gpu_us: C 3,488 vs D2 3,378  ->  D2 is faster  (1.03x)
