  WHY THE INERT KNOBS ARE INERT IS NOT ONE REASON, and the
  difference is the whole taxonomy:

    USE_TC / TC_SELECT / TC_OPT -- their ONLY reads are inside
      `if USE_TC > 0 and (one reduce axis or TC_OPT>=1)`
      (codegen/opt/heuristic.py:28,32). This kernel has no
      reduction axis at all: every output element is a pure
      function of one output index. So the guard is false and the
      value is never consulted. TC_OPT=1 and TC_OPT=2 flip that
      guard's SECOND disjunct and are STILL byte-identical -- a
      measurement, not an inference, and it closes the reading that
      TC_OPT could reach this kernel that way.
      Class: (i) for this workload. Not a compiler defect; a
      GEMM knob and a non-GEMM kernel.

    ALLOW_TF32 -- its only consumer filters tensor-core selection
      (postrange.py:226), and on sm_75 there is no fp32 tensor core
      for it to admit: `cuda_sm75 = cuda_8168_f16` (tc.py:94,98) is
      half-input only. So the answer is partly an ARCHITECTURE
      fact, and this knob's class is (iv), not (i) or (ii). On an
      sm_80 card -- where `cuda_8168_tf32` exists -- the same sweep
      would answer a different question.

    IMAGE -- redirects `dot`/`conv2d` to texture forms
      (mixin/op.py:386,1593) and 4-wide vectorises image-shaped
      buffers (heuristic.py:47). The DDA gathers from a 3-D volume,
      so none applies. Inert because of the SHAPE of the workload:
      the capability exists, this kernel is not one it covers. That
      is not (i) -- (i) is 'cannot express', and the DDA is expressed.

    TRANSCENDENTAL -- the ONE reachable knob with a real effect, and
      it is NEGATIVE. The registry predicted the DDA kernel would
      grow, because `rsqrt()` lowers to SQRT + RECIPROCAL (measured:
      the op set of `Tensor([4.,9.]).rsqrt()` is {SQRT, RECIPROCAL})
      and transcendental.py:275-276 rewrites SQRT to a software `pow`
      when the flag is >= 2. It grew, on BOTH ports, by the same
      ~450 source lines and ~970 SASS -- the emitted CUDA goes from
      `1/sqrt(...)` to a ~28-line software pow with a `tg_bitcast`
      exponent extraction and a degree-7 polynomial.
      The prediction was right about the MECHANISM and the knob is
      still useless here: the DDA needs one square root per ray in
      the PROLOGUE, not on the hot path, and this knob only makes
      that one more expensive. It is the clearest example in the
      sweep of a knob that works exactly as documented and buys
      nothing for this workload.

    NOLOCALS -- the one knob that reaches the scheduler's shape
      decisions, and the only row whose verdict this table cannot
      finish. See the state name in the table above.

    OPT_LEVEL -- on the brief's list and NOT IN THIS VERSION. It is
      not a ContextVar: `Context(OPT_LEVEL=0)` raises KeyError, and
      there is no definition line in helpers.py to find. The nearest
      real knobs are NOOPT and BEAM (both helpers.py:232) and NEITHER
      is on the list, so substituting one would answer a different
      question. Recorded as an absence. A row reading 'no effect'
      would be a null result about a knob that was never set -- the
      same category error as the USE_TC/TC naming trap.

  MODELLED, and marked as such. Arithmetic on MEASURED SASS
  (this arm's own cubins) plus TWO figures read out of notes/19:
  the reference's 776 (§4.0.1, re-derived there from its SASS) and
  its measured mean of 26.4 steps/pixel (§1.3). The 26.4 is the
  one input that needs a device and this file does not re-derive
  it; a reader who wants it re-measured should take it from
  `minecu_ref/bench/bench.cu`'s own probe on the same card.

  WHY RE-DERIVE AT ALL, given derivation/minecu_gap.py exists.
  That module divides into 36 600, which is notes/19's whole-graph
  total for the NAIVE port. This arm's totals are different
  objects -- the lean port's hot kernel, and the naive port's hot
  kernel alone -- so reusing its 9.73x against a different
  numerator is the category error C-14 exists to prevent.

  NOTE ON THE 776. It is notes/19's figure, read out of
  `minecu_ref/build/kernels_sm_75.sass` and re-derived in
  notes/19 §4.0.1 (152 prologue + 16x38 body + 16 epilogue). It
  is the ONE number in this note this arm did not produce, and
  it is the hand-written side, so producing it is arm A's job.
  Everything in the `SASS/step` column for the generated side is
  MEASURED here, from cubins this arm compiled.

  the PORT term, MEASURED:  1137.0 -> 795.8 SASS/step = 1.429x.  So 30.0% of the naive port's
  per-step cost was the port's own index arithmetic -- cause (a),
  real, and removed.
  what is LEFT:             795.8 SASS/step = 16.4x the reference. That residue is the
  LOWERING: cause (b), expressible and not found, NOT the port.

  So C-14 is right that the port's index arithmetic was a real
  defect, and wrong to imply the port was the remaining story:
  fixing it recovered 1.43x of a 46.9x instruction gap.

  REFUSED: the SASS-per-source-op ratio. The compiler REPLICATES
  the voxel gather -- the lean kernel's emitted CUDA has 496 reads
  of the voxel buffer, not 32, and they are 16 step bodies ~400
  lines apart plus a 481-read tail. The denominator is not
  establishable, so the ratio is not reported.
